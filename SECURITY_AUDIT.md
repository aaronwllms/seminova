## Executive summary

- **No Critical or High findings.** Open: 3 Medium, 8 Low. Accepted: 1 Low with an ID plus 5 standing risks. Nothing found that lets one user reach another user's data.
- **Resolved this window — Next.js upgraded to 16.3.3 (S006, W7):** `next` moved 16.2.9 → 16.3.3, closing the July 2026 advisory set. Note the target moved after this audit was written: S006 specified 16.2.11, but the August 25 release advanced Active LTS to 16.3 and patched two Critical advisories in 16.3.3 / 15.5.24 only — 16.2.11 does not receive them. **The two August Criticals have not been individually assessed for applicability to this app's configuration**, unlike the per-CVE analysis S006 performed for July; see § Human / tooling follow-ups.
- **Medium — unauthenticated RPC reachable (S007, W2):** `purge_expired_app_logs()` (SECURITY DEFINER, deletes from `app_logs`) revokes EXECUTE from `public` only. Supabase default-grants EXECUTE to `anon` and `authenticated` on every new `public` function, and `REVOKE … FROM PUBLIC` does not remove those role grants — the repo's own `20260720151459` migration revokes all three roles for exactly this reason.
- **Medium — password-recovery flag stamp is fire-and-forget (S008, W1/W3):** `void markHasPasswordAction()` after a successful `updateUser({ password })`. If that call is lost, the account keeps `has_password = false` and therefore keeps the reauth-free elevated first-password path open — the precise drift risk [ADR-0012](docs/adr/ADR-0012-first-password-elevated-write-gated-on-flag.md) names.
- **Medium — 6-character minimum password (S009, W1):** below every current baseline, with no breach-corpus check. Dashboard setting plus the mirrored constant; PM decision.
- **Verified sound (W1–W5):** owner-scoped `profiles` RLS with column-level UPDATE grants that genuinely protect `has_password`; admin-gated `app_settings` / `app_logs` RLS with no client INSERT/DELETE; owner-folder storage RLS with no SVG in the MIME allowlist; SECURITY DEFINER admin RPCs with in-function gates, `search_path = ''`, and static ORDER BY allowlists (no dynamic SQL); PostgREST filter injection escaped on the log search path; cursor pagination integer-validated; secret key absent from client bundles; open-redirect and avatar-origin guards; sanitized auth errors.
- **Cache safety (W6):** `cacheComponents: true` with no `'use cache'` anywhere; every per-user read passes through `cookies()` and is therefore dynamic; `unstable_cache` holds only the global settings snapshot. No cross-user response caching found.
- **Supabase security advisors:** not run this pass — the Supabase MCP server was unavailable (loading / unauthenticated). Re-run `get_advisors` when it reconnects.

## Verified OK

- **W1 — Auth & routing:** public routes are `/`, `/auth/**`, `/terms`, `/privacy`, `/reference`, `/features`, `/workflow`, and `/api/client-logs`, matching AGENTS.md § Hard constraints. Unauthenticated users on protected routes are signed out locally and redirected to `/auth/login` with a same-origin-validated `next`; a stray auth `code` redirects to `/auth/error?source=stray_code` instead. Non-admins on `/admin/**` are redirected at the proxy and again in `AdminAuthGate`. `/auth/confirm` validates optional `next` through `isUsableRedirectNext`; `login-form` and `sign-in-link-form` validate through `isSafeRedirect` against `window.location.origin`. Protocol-relative (`//evil.com`) and cross-origin targets are rejected. Production proxy returns 503 when Supabase env is missing; `scripts/checks/supabase-env.mjs` blocks the build. Display reads use `getDisplayAuthClaims()` (signature verified, `allowExpired: true`) per [ADR-0005](docs/adr/ADR-0005-proxy-session-gate-two-authority-refresh.md) — expired-but-signed tokens can render shell chrome, but every data path re-gates through `getUser()` or RLS.
- **W2 — RLS and DB functions:** RLS enabled on all three custom tables. `profiles` — owner-scoped SELECT/INSERT/UPDATE; `revoke update … from authenticated` plus `grant update (display_name, avatar_url, bio)` means `has_password` is genuinely not client-writable, and the absent DELETE policy blocks the delete-then-reinsert route around it. `app_settings` and `app_logs` — admin JWT gate on every allowed operation, with no client INSERT/DELETE policy so writes go only through the service client. All five SECURITY DEFINER functions set an explicit `search_path`; `handle_new_user` and `rls_auto_enable` are revoked from `public`, `anon`, and `authenticated`. Admin RPCs gate in-function and build `ORDER BY` from a static `CASE WHEN` allowlist — no dynamic SQL — with `ILIKE` search escaped and a 3-character floor. The `ensure_rls` event trigger auto-enables RLS on new `public` tables. Realtime publishes only `app_logs`; RLS admin-only SELECT means non-admin subscribers receive no payloads, and the app hook discards payloads entirely, using them only as an invalidation signal.
- **W3 — Server surface:** all 17 actions authenticate before doing work — profile actions via `getUser()` then zod then `.eq('id', user.id)`; every admin action via `assertAdminCaller()` (which uses `getUser()`, not cached claims) before touching a session or service client. No IDOR: owner IDs come from the session, never from input. Self-demotion and self-ban are blocked. Admin list inputs are allowlist-validated (page size, sort column, sort direction, ban duration, log levels); log cursors require a positive integer `id` and a valid timestamp, so the interpolated PostgREST `or()` filter cannot be manipulated; log search escapes `%`, `_`, `\` and quotes values containing `,()`. `POST /api/client-logs` verifies origin, validates against a closed key registry and zod schema, and caps payloads before forwarding. Auth errors are fallback-first through `extractAuthFormError` — Supabase's raw messages never reach users, and `invalid_credentials` / `email_not_confirmed` share one message so user existence is not leaked. The single `dangerouslySetInnerHTML` is landing-page JSON-LD built server-side from site config and unicode-escaped by its builder. No SSRF surface: no server-side fetch of user-supplied URLs.
- **W4 — Storage:** `avatars` is intentionally public-read. Write policies scope INSERT/UPDATE/DELETE to the owner's folder via `(storage.foldername(name))[1] = auth.uid()`. Bucket enforces a 2 MB cap and a JPEG/PNG/WebP allowlist that excludes SVG, removing the stored-XSS vector; stored objects are served from the Supabase origin, not the app origin. The client verifies the session user matches `userId` before uploading; the server action rejects non-owned URLs and then rebuilds the canonical public URL rather than trusting the submitted one.
- **W5 — Secrets and exposure:** `SUPABASE_SECRET_KEY` appears only in `src/utils/env.ts` and is consumed only by `src/supabase/service.ts` and `scripts/admin/`. Grepping the built `.next/static` output for `sb_secret_`, `service_role`, and `SUPABASE_SECRET` returns nothing — the key is not inlined into client bundles. `.env.local` is untracked and matched by `.gitignore`; no `.env.local` appears in git history; `.env.example` holds placeholders only. Service-client imports are limited to four server modules by an ESLint default-deny allowlist. DTO discipline holds: the admin user list maps RPC rows to explicit display fields rather than returning raw `app_metadata`, log rows select an explicit column list, and public/authenticated banner slots forward only the one relevant banner config even though the settings snapshot is fetched with the service client.
- **W6 — Transport and cache safety:** headers are applied globally via `next.config.ts` → `getSecurityHeaders()` on `/:path*`. A single enforced `Content-Security-Policy` (no Report-Only companion) carries `default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `font-src 'self'`, and Supabase-scoped `img-src` / `connect-src`; `'unsafe-eval'` is development-only; `X-Frame-Options: DENY` and HSTS accompany it, all pinned by unit tests. Mutations are server actions (Next.js origin verification); the one custom API route re-implements origin verification explicitly; `/auth/confirm` is a token-bound GET. On caching: `cacheComponents: true` with zero `'use cache'` directives, `unstable_cache` used only for the global settings snapshot under a coarse tag ([ADR-0006](docs/adr/ADR-0006-settings-reads-cached-under-one-coarse-tag.md)), `React.cache` (request-scoped, not cross-request) on the profile read, `connection()` on the authenticated banner slot, and every per-user read reaching `cookies()` — no path found where one user's response could be served to another.
- **W7 — Dependency hygiene:** `react@19.2.3`, `@supabase/ssr@0.8.0`, and `@supabase/supabase-js@2.105.4` carry no known advisories at audit time and resolve from the lockfile. No floating semver on security-relevant packages. No custom server, no `rewrites`/`redirects`, no `images.remotePatterns`, and no Edge-runtime actions — which is what ruled out five of the nine July Next.js advisories recorded in S006 (§ Resolved).
