## Executive summary

- **No Critical or High findings.** Open: 1 Medium, 4 Low. Accepted: 1 Low with an ID plus 5 standing risks. Nothing found that lets one user reach another user's data.
- **Resolved this window — Next.js upgraded to 16.3.3 (S006, W7):** `next` moved 16.2.9 → 16.3.3, closing the July 2026 advisory set. Note the target moved after this audit was written: S006 specified 16.2.11, but the August 25 release advanced Active LTS to 16.3 and patched two Critical advisories in 16.3.3 / 15.5.24 only — 16.2.11 does not receive them. **The two August Criticals have not been individually assessed for applicability to this app's configuration**, unlike the per-CVE analysis S006 performed for July; see § Human / tooling follow-ups.
- **Resolved this window — leftover client EXECUTE revoked on public functions (S007, S016, W2):** `purge_expired_app_logs()` no longer grants EXECUTE to `anon` or `authenticated` (pg_cron as owner is unchanged). `admin_list_users` / `admin_user_stats` no longer grant EXECUTE to `anon`; `authenticated` stays so the admin users page still works. Verification pending until after `pnpm db:push`.
- **Resolved this window — has_password is server-authoritative (S008, S013, W1/W2/W3):** the signup trigger always inserts `false`; password sign-up and recovery each stamp on the same awaited server path that wrote the password. Direct client metadata can no longer set the flag. Manually verified 2026-08-28 (Epic 2 checklist: direct `signUp` with metadata, in-app sign-up, magic-link, recovery, Change Password unchanged, confirm-email host).
- **Resolved this window — baseline response headers (S010, W6):** `getSecurityHeaders()` now emits Referrer-Policy, X-Content-Type-Options (nosniff), and a restrictive Permissions-Policy alongside the existing CSP, X-Frame-Options, and HSTS. HSTS stays unconditional in development (RFC 6797 no-op on HTTP). Verification pending — the three headers on a deployed preview.
- **Medium — 6-character minimum password (S009, W1):** below every current baseline, with no breach-corpus check. Dashboard setting plus the mirrored constant; PM decision.
- **Verified sound (W1–W5):** owner-scoped `profiles` RLS with column-level UPDATE grants that genuinely protect `has_password`; admin-gated `app_settings` / `app_logs` RLS with no client INSERT/DELETE; owner-folder storage RLS with no SVG in the MIME allowlist; SECURITY DEFINER admin RPCs with in-function gates, `search_path = ''`, and static ORDER BY allowlists (no dynamic SQL); PostgREST filter injection escaped on the log search path; cursor pagination integer-validated; secret key absent from client bundles; open-redirect and avatar-origin guards; sanitized auth errors.
- **Cache safety (W6):** `cacheComponents: true` with no `'use cache'` anywhere; every per-user read passes through `cookies()` and is therefore dynamic; `unstable_cache` holds only the global settings snapshot. No cross-user response caching found.
- **Supabase security advisors:** not run this pass — the Supabase MCP server was unavailable (loading / unauthenticated). Re-run `get_advisors` when it reconnects.

- **Client log relay abuse ([ADR-0007](docs/adr/ADR-0007-client-log-relay-unauthenticated.md)):** unauthenticated, same-origin `POST /api/client-logs` persists rows at/above `min_log_level` via the service client. Bounded by the closed key registry, tag namespace, payload caps, retention purge, and level threshold — not by request count. Origin verification fails closed when both `Origin` and `Referer` are absent, but a non-browser client can forge `Origin`, so it is CSRF protection, not authentication. **Why accepted:** template scope per the ADR. **Reopen when:** production scale or observed abuse — rate-limit at WAF/CDN or in-app (tech-debt F082).
- **App-level rate limiting:** Supabase Auth throttles its own sign-in, OTP, and email-send endpoints. Server actions and the client-log relay have no app-level throttle. **Why accepted:** current scope. **Reopen when:** abuse is observed, custom API routes expand, or S009 is resolved without a throttle.
- **`style-src 'unsafe-inline'`:** required for Tailwind inline styles. **Why accepted:** standard Next.js compatibility. **Reopen when:** a nonce/hash strategy for styles is viable (pairs with S004 / tech-debt F095).
- **Client-side avatar validation and resize:** MIME and size are checked in the browser before upload; bucket `allowed_mime_types` (no SVG), `file_size_limit`, and folder-scoped RLS are the server-side enforcement. A user bypassing the UI can store an unresized image, or bytes that are not really an image, under `Content-Type: image/*` on the Supabase origin. **Why accepted:** authenticated users are confined to their own folder and Supabase Storage is the trust boundary. **Reopen when:** the threat model requires server-side re-encoding.
- **Admin-configured banner links:** `parseBannerMessage` / `BannerMessage` render admin-set headline and detail as React text nodes with `isSafeUrlScheme`-validated hrefs — no raw HTML. **Why accepted:** expected admin trust model. **Reopen when:** non-admin authors can set banner copy.

## Verified OK

- **W1 — Auth & routing:** public routes are `/`, `/auth/**`, `/terms`, `/privacy`, `/reference`, `/features`, `/workflow`, and `/api/client-logs`, matching AGENTS.md § Hard constraints. Unauthenticated users on protected routes are signed out locally and redirected to `/auth/login` with a same-origin-validated `next`; a stray auth `code` redirects to `/auth/error?source=stray_code` instead. Non-admins on `/admin/**` are redirected at the proxy and again in `AdminAuthGate`. `/auth/confirm` validates optional `next` through `isUsableRedirectNext`; `login-form` and `sign-in-link-form` validate through `isSafeRedirect` against `window.location.origin`. Protocol-relative (`//evil.com`) and cross-origin targets are rejected. Production proxy returns 503 when Supabase env is missing; `scripts/checks/supabase-env.mjs` blocks the build. Display reads use `getDisplayAuthClaims()` (signature verified, `allowExpired: true`) per [ADR-0005](docs/adr/ADR-0005-proxy-session-gate-two-authority-refresh.md) — expired-but-signed tokens can render shell chrome, but every data path re-gates through `getUser()` or RLS.
- **W2 — RLS and DB functions:** RLS enabled on all three custom tables. `profiles` — owner-scoped SELECT/INSERT/UPDATE; `revoke update … from authenticated` plus `grant update (display_name, avatar_url, bio)` means `has_password` is genuinely not client-writable, and the absent DELETE policy blocks the delete-then-reinsert route around it. `app_settings` and `app_logs` — admin JWT gate on every allowed operation, with no client INSERT/DELETE policy so writes go only through the service client. All five SECURITY DEFINER functions set an explicit `search_path` and are locked down at the EXECUTE grant: `handle_new_user`, `rls_auto_enable`, and `purge_expired_app_logs` are revoked from `public`, `anon`, and `authenticated`; `admin_list_users` and `admin_user_stats` are revoked from `anon` and remain granted to `authenticated`. Admin RPCs gate in-function and build `ORDER BY` from a static `CASE WHEN` allowlist — no dynamic SQL — with `ILIKE` search escaped and a 3-character floor. The `ensure_rls` event trigger auto-enables RLS on new `public` tables. Realtime publishes only `app_logs`; RLS admin-only SELECT means non-admin subscribers receive no payloads, and the app hook discards payloads entirely, using them only as an invalidation signal.
- **W3 — Server surface:** 17 of 18 actions authenticate before doing work — profile actions via `getUser()` then zod then `.eq('id', user.id)`; every admin action via `assertAdminCaller()` (which uses `getUser()`, not cached claims) before touching a session or service client. The exception is `signUpWithPasswordAction`, which is reachable without a session; its only service-client write targets the account the caller just created. No IDOR: owner IDs come from the session, never from input. Self-demotion and self-ban are blocked. Admin list inputs are allowlist-validated (page size, sort column, sort direction, ban duration, log levels); log cursors require a positive integer `id` and a valid timestamp, so the interpolated PostgREST `or()` filter cannot be manipulated; log search escapes `%`, `_`, `\` and quotes values containing `,()`. `POST /api/client-logs` verifies origin, validates against a closed key registry and zod schema, and caps payloads before forwarding. Auth errors are fallback-first through `mapAuthError` / `extractAuthFormError` — Supabase's raw messages never reach users, and `invalid_credentials` / `email_not_confirmed` share one message so user existence is not leaked. The single `dangerouslySetInnerHTML` is landing-page JSON-LD built server-side from site config and unicode-escaped by its builder. No SSRF surface: no server-side fetch of user-supplied URLs.
- **W4 — Storage:** `avatars` is intentionally public-read. Write policies scope INSERT/UPDATE/DELETE to the owner's folder via `(storage.foldername(name))[1] = auth.uid()`. Bucket enforces a 2 MB cap and a JPEG/PNG/WebP allowlist that excludes SVG, removing the stored-XSS vector; stored objects are served from the Supabase origin, not the app origin. The client verifies the session user matches `userId` before uploading; the server action rejects non-owned URLs and then rebuilds the canonical public URL rather than trusting the submitted one.
- **W5 — Secrets and exposure:** `SUPABASE_SECRET_KEY` appears only in `src/utils/env.ts` and is consumed only by `src/supabase/service.ts` and `scripts/admin/`. Grepping the built `.next/static` output for `sb_secret_`, `service_role`, and `SUPABASE_SECRET` returns nothing — the key is not inlined into client bundles. `.env.local` is untracked and matched by `.gitignore`; no `.env.local` appears in git history; `.env.example` holds placeholders only. Service-client imports are limited to five server modules by an ESLint default-deny allowlist. The fifth (`sign-up/actions.ts`) is the first service-client call site reachable without authentication; its only reachable write targets the account the caller just created. DTO discipline holds: the admin user list maps RPC rows to explicit display fields rather than returning raw `app_metadata`, log rows select an explicit column list, and public/authenticated banner slots forward only the one relevant banner config even though the settings snapshot is fetched with the service client.
- **W6 — Transport and cache safety:** headers are applied globally via `next.config.ts` → `getSecurityHeaders()` on `/:path*`. A single enforced `Content-Security-Policy` (no Report-Only companion) carries `default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `font-src 'self'`, and Supabase-scoped `img-src` / `connect-src`; `'unsafe-eval'` is development-only; `X-Frame-Options: DENY`, HSTS (emitted in development by design — RFC 6797 no-op on HTTP), `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, and a restrictive Permissions-Policy accompany it, all pinned by unit tests. Mutations are server actions (Next.js origin verification); the one custom API route re-implements origin verification explicitly; `/auth/confirm` is a token-bound GET. On caching: `cacheComponents: true` with zero `'use cache'` directives, `unstable_cache` used only for the global settings snapshot under a coarse tag ([ADR-0006](docs/adr/ADR-0006-settings-reads-cached-under-one-coarse-tag.md)), `React.cache` (request-scoped, not cross-request) on the profile read, `connection()` on the authenticated banner slot, and every per-user read reaching `cookies()` — no path found where one user's response could be served to another.
- **W7 — Dependency hygiene:** `react@19.2.3`, `@supabase/ssr@0.8.0`, and `@supabase/supabase-js@2.105.4` carry no known advisories at audit time and resolve from the lockfile. No floating semver on security-relevant packages. No custom server, no `rewrites`/`redirects`, no `images.remotePatterns`, and no Edge-runtime actions — which is what ruled out five of the nine July Next.js advisories recorded in S006 (§ Resolved).

## Human / tooling follow-ups

- **Assess the two August 2026 Next.js Critical advisories** against this app's configuration, the way S006 did for the July set — CVE IDs, affected-configuration preconditions, and whether each was reachable on 16.2.9. The 16.3.3 upgrade closes them regardless, but the audit should record applicability rather than assume it.
- **S007 / S016 verification (highest value):** after `pnpm db:push`, in the SQL editor confirm `has_function_privilege('anon', …, 'execute')` is false for `purge_expired_app_logs()`, `admin_list_users(text, text, integer, integer, text, boolean, boolean, boolean)`, and `admin_user_stats()`; `has_function_privilege('authenticated', …)` is false for the purge function and true for the two admin RPCs. Then `select proname, proacl from pg_proc where pronamespace = 'public'::regnamespace;` — no `public` function should still carry a client EXECUTE grant beyond `admin_list_users` / `admin_user_stats` to `authenticated`. Record those results in the S007 Resolved row and delete this bullet.
- Re-run the Supabase MCP `get_advisors` security lints once the server reconnects — they were unavailable this pass.
- Manual IDOR test with two accounts: neither can read or update the other's `profiles` row via the browser client or `updateProfileAction`.
- Manual admin bypass test with a non-admin session: hit `/admin/users`, `/admin/logs`, `/admin/settings` and invoke the admin actions directly; expect redirects and operational 403-style envelopes.
- Manual RLS test: `anon` cannot SELECT `profiles`, `app_settings`, or `app_logs`; a non-admin authenticated user cannot SELECT `app_settings` or `app_logs`; user B cannot UPDATE user A's profile; no user can UPDATE their own `has_password`.
- Manual Realtime test: a non-admin authenticated client subscribes to the `app_logs` INSERT channel and receives no row payloads.
- Manual relay test: cross-origin POST without matching `Origin`/`Referer` returns 403; a tag key outside the registry returns 400; rows appear only at/above the configured `min_log_level`.
- S009 confirmation: check the Supabase Dashboard for the live minimum password length and whether leaked-password protection is on, then confirm `MIN_PASSWORD_LENGTH` mirrors it. Also confirm whether `auth.admin.updateUserById` (the first-password path) applies the project's password policy — if it does not, the app-side zod floor is the only check on that route.
- S010: verify on a deployed preview in DevTools that `Referrer-Policy`, `X-Content-Type-Options`, and `Permissions-Policy` are present alongside enforced `Content-Security-Policy` (no Report-Only companion).
- S011 decision input: check the project's configured access-token TTL, since that is the exact size of the demotion/ban window.
